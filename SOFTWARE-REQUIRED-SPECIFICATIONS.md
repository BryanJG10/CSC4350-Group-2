# Dining Hall Review App
# Software Requirements Specification

## Introduction
### Purpose
This Software Requirements Specification (SRS) defines the purpose, scope, users, functional requirements, non-functional requirements, interfaces, data requirements, architecture, and technology decisions for our Dining Hall Review App. The document establishes a shared baseline for the team before and during implementation, so it is subject to change.
### Scope
Dining Hall Review is a web application for GSU students on meal plans to view and submit peer ratings and reviews for stations and menu items at Patton Dining Hall, Piedmont Central Dining Hall, and Piedmont North Dining Hall. The system supports search and filtering by dining hall, station, menu item, meal period, rating, and dietary/allergen information. Users can save favorite meals or individual items and request heads-up notifications when a saved item is scheduled to be available. PantherDining staff can use structured feedback and aggregate trends to identify items or stations that may need attention

## Overall Description
Dining Hall Review is a web-based review and discovery app layered around GSU dining information. Unlike a menu-publishing system that primarily tells students what is being served, this application adds student-generated ratings, reviews, structured feedback tags, saved items, and heads-up notifications.
### User Needs
*   Students need current peer feedback before choosing where to eat.
*   Students need station- and item-level information instead of only dining-hall-level information.
*   Students with dietary or allergen concerns need searchable and filterable structured tags.
*   Students need a way to save favorite meals/items and receive a heads-up when saved items are scheduled.
*   PantherDining staff need organized feedback by dining hall, station, and item.
*   PantherDining staff need aggregate rating history and trends that are easier to act on than scattered comments.
### User Roles
| **Role** | **Responsibility** |
|----------|---------------------|
| GSU Student | Browses dining information, searches/filters items, reads and submits reviews, saves items, and manages heads-up alerts. |
| PantherDining Staff/Admin | Manages menu/station information, reviews/moderates student feedback, and views aggregate analytics. |
| Notification Service | External supporting service that delivers heads-up notifications generated by the application. |
### Assumptions and Dependencies
*   Users can access the application through a modern web browser.
*   The three target dining halls are Patton, Piedmont Central, and Piedmont North.
*   Menu availability data must exist in the application's database for the heads-up feature to trigger.
*   A future integration with a campus menu source may be used to import menu data; the project should not assume access to an undocumented external API.
*   Student authentication should be tied to a GSU account or another approved identity mechanism if such an integration is available.
*   Notification delivery depends on the availability and configuration of the selected notification service.
### Design Constraints
The project is a web application and should be implementable within the team's course-project schedule.

The relational model must support halls, stations, menu items, users, reviews, and dietary/allergen tags.

The team must maintain clear separation between frontend, backend, database, and testing responsibilities.

Features requiring unavailable external systems, such as verified meal-swipe transactions, should be treated as future enhancements unless an approved integration is provided.

## System Features and Functional Requirements
The following requirements are written as testable 'shall' statements. They describe what the system must do rather than prescribing implementation details, consistent with the distinction between functional and non-functional requirements
### Account and Authentication
FR-01: The system shall allow a student to create or access an authorized account.

FR-02: The system shall authenticate users before allowing account-specific actions.

FR-03: The system shall allow authenticated users to view and update their profile information.

FR-04: The system shall distinguish Student and PantherDining Staff/Admin permissions.
### Dining Hall, Station, and Menu Browsing
FR-05: The system shall display the three supported dining halls.

FR-06: The system shall display stations associated with each dining hall.

FR-07: The system shall display menu items associated with each station and meal period.

FR-08: The system shall display available rating, review, dietary/allergen, and availability information for a selected item.

FR-09: The system shall allow students to navigate from a dining hall to its stations and menu items.
### Search and Filtering
FR-10: The system shall allow users to search for menu items.

FR-11: The system shall allow users to filter results by dining hall.

FR-12: The system shall allow users to filter results by station.

FR-13: The system shall allow users to filter results by meal period.

FR-14: The system shall allow users to filter results by rating.

FR-15: The system shall allow users to filter results by dietary/allergen tags.

FR-16: The system shall display an appropriate message when no matching results are found.
### Ratings and Reviews
FR-17: The system shall allow an authenticated student to submit a rating for an eligible menu item.

FR-18: The system shall allow an authenticated student to submit a written review.

FR-19: The system shall allow students to associate supported structured tags with a review.

FR-20: The system shall display aggregate ratings for menu items and stations.

FR-21: The system shall display review history for a selected menu item.

FR-22: The system shall allow a student to edit or delete their own review subject to system rules.

FR-23: The system shall prevent duplicate reviews for the same user/item/visit when visit-level review tracking is enabled.

FR-24: The system shall provide mechanisms for detecting or limiting spam and abusive submissions.
### Saved Items and Heads-Up Notifications
FR-25: The system shall allow a student to save a menu item as a favorite.

FR-26: The system shall allow a student to save a favorite meal or meal combination when supported by the data model.

FR-27: The system shall allow a student to remove a saved item or meal.

FR-28: The system shall allow a student to enable or disable heads-up alerts for a saved item.

FR-29: The system shall compare scheduled menu availability with active heads-up subscriptions.

FR-30: The system shall generate a heads-up notification when a subscribed item is scheduled to be available.

FR-31: The system shall record notification status so the same scheduled alert is not repeatedly sent for the same event unless configured otherwise.
### Staff/Admin and Analytics
FR-32: The system shall allow authorized PantherDining staff/admin users to manage dining hall, station, and menu records.

FR-33: The system shall allow authorized staff/admin users to view student reviews.

FR-34: The system shall allow authorized staff/admin users to moderate reviews according to defined moderation rules.

FR-35: The system shall display aggregate ratings by dining hall, station, and menu item.

FR-36: The system shall provide semester-long review history and trend information.

FR-37: The system shall allow staff/admin users to identify changes in rating performance over time.

FR-38: The system shall restrict administrative functions to authorized staff/admin accounts.
### Data Integrity
FR-39: The system shall enforce required relationships between users, reviews, menu items, stations, dining halls, and tags.

FR-40: The system shall preserve review timestamps and associated menu-item information.

FR-41: The system shall maintain many-to-many relationships between menu items and dietary/allergen tags.

FR-42: The system shall maintain consistent aggregate rating calculations when reviews are added, edited, or removed.

## Non-Functional Requirements
### Usability
NFR-01:The system shall use a consistent navigation structure and visual style across pages.

NFR-02: A student shall be able to reach a menu item's ratings/reviews without navigating through unnecessary pages.

NFR-03: Search and filter controls shall use understandable labels.

NFR-04: The interface shall provide clear feedback after review submission, saving an item, changing an alert, or completing another account action.

NFR-05: The application shall support keyboard-accessible navigation for core interactions.
### Accessibility
NFR-06: The interface shall provide readable text, meaningful labels, and accessible form controls.

NFR-07: Important information shall not be conveyed by color alone.

NFR-08: Images/icons used for meaningful content shall have appropriate alternative text or accessible labels.
### Performance
NFR-09: Under normal project loads, common browsing, search, and review-display requests should return within 2 seconds after the server receives the request.

NFR-10: The system should support concurrent peak-meal-period users without noticeable degradation of core browsing and review functions.

NFR-11: Rating aggregates should be cached or efficiently queried so that frequent reads do not unnecessarily overload the database.
### Reliability & Availability
NFR-12: The system shall preserve committed reviews and saved-item changes after successful submission.

NFR-13: Database failures shall not result in partially committed review records.

NFR-14: The application shall log application errors sufficient for developers to diagnose failures.

NFR-15: The notification workflow shall tolerate temporary notification-service failures by retaining an appropriate retry/error status.
### Security
NFR-16: Data transmitted between the browser and server shall use HTTPS.

NFR-17: Passwords shall never be stored as plaintext.

NFR-18: The backend shall enforce authorization on administrative endpoints rather than relying only on frontend controls.

NFR-19: User input shall be validated and safely handled to reduce injection and other common web vulnerabilities.

NFR-20: Sessions/tokens shall expire according to the authentication strategy.

NFR-21: Administrative actions shall be auditable through appropriate logs.
### Scalability and Maintainability
NFR-22: The application shall use a modular separation between frontend, backend, and database responsibilities.

NFR-23: The database schema shall be normalized enough to avoid unnecessary duplication of core dining data.

NFR-24: Source code shall be maintained in a version-control system.

NFR-25: Configuration values such as database credentials and notification-service keys shall not be hard-coded into source files.

NFR-26: The application shall support current versions of major modern browsers such as Chrome, Edge, Firefox, and Safari.

NFR-27: The interface shall be usable on desktop and mobile-sized screens.

## Data Requirements
The core relational entities identified for the project are:
| **Entity** | **Purpose** |
|----------------------|--------------------------------------------------------|
| Users | Account identity, role, and profile information. |
| Dining Halls | Patton, Piedmont Central, and Piedmont North. |
| Stations | Stations belonging to a dining hall. |
| Menu Items | Food items offered by a station for a meal period/date. |
| Reviews | Student rating/review records associated with a user and menu item. |
| Dietary/Allergen Tags | Structured tags applied to menu items and/or supported review classifications. |
| Menu Availability | Scheduled availability used by browsing and heads-up alerts. |
| Saved Items | Student-to-menu-item saved/favorite relationships. |
| Heads-Up Subscriptions | Student subscriptions requesting alerts for saved/specified items. |
| Notification Events | Records of generated/delivered/failed heads-up notifications. |

**Key relationships**: a Dining Hall has many Stations; a Station has many Menu Items; a User has many Reviews; a Menu Item has many Reviews; Menu Items and Dietary/Allergen Tags have a many-to-many relationship; Users and Menu Items have a many-to-many relationship through Saved Items; Heads-Up Subscriptions connect users to items/scheduled availability.

## Architecture and Tech Decisions
see [ARCHITECTURE.md](ARCHITECTURE.md) for the diagrams and file layout
everything is built from; as well as more in depth architectural information

The recommended architecture is a three-tier web architecture: presentation layer, application/API layer, and relational data layer. This matches the team's separation of frontend, backend, database, and testing responsibilities.
| **Layer/Technology** | **Choice** | **Reason** |
|----------------------|--------------------------------------------------------|-------------------------------------------------------|
| Frontend | React + JavaScript/TypeScript + HTML/CSS | Build the responsive GUI, navigation, search/filter controls, review forms, saved-item screens, and staff dashboard. |
| Backend | Java + Spring Boot + REST API | Implement authentication/authorization, review rules, filtering, aggregation, saved items, heads-up logic, and admin functions. |
| Database | MySQL | Store normalized relational data for users, halls, stations, items, reviews, tags, saved items, availability, and notification events. |
| Data Access | Spring Data JPA / Hibernate | Map Java domain objects to relational tables and reduce repetitive database-access code |
| Testing | JUnit + Spring Boot Test, frontend component tests as appropriate | Test business rules, API endpoints, integration behavior, and critical UI workflows. |
| Version Control | Git/GitHub | Coordinate team development, code review, and configuration management. |
| Deployment/Cloud | Cloud-hosted application and managed MySQL instance | Provide a shared environment for the team and final demonstration, exact provider can be selected based on course constraints. |
| Notifications | Email or browser notification provider | Deliver heads-up alerts, provider choice depends on available project infrastructure. |
### Flow
Student/Staff browser -> React frontend -> Spring Boot REST API -> MySQL database

Spring Boot applies authorization and business rules before reading or modifying database records.

Heads-up scheduler/service checks scheduled menu availability against active subscriptions and sends notifications through the selected notification service.

Staff analytics are generated from stored review history and aggregate queries rather than from manually collected feedback.

## Security and Privacy
Authentication shall be required for account-specific actions such as submitting reviews, saving items, and managing alerts.

Authorization shall be enforced server-side for PantherDining staff/admin operations.

Passwords, if managed by the application, shall be salted and securely hashed.

HTTPS shall protect credentials, reviews, profile data, and other application traffic in transit.

Only information necessary for the application's functions should be stored.

Administrative and moderation actions should be logged without exposing credentials or sensitive secrets.

## Risks and Possibe Future Enhancements
| **Risk** | **Impact** | **Mitigation** |
|----------------------|--------------------------------------------------------|-------------------------------------------------------|
| Menu-data availability | The heads-up feature depends on accurate scheduled menu data. | Use a controlled menu-data source for the MVP and design the backend so a future approved import can be added. |
| Review abuse | Spam, duplicate accounts, and review bombing can reduce trust. | Require authentication, enforce review-integrity rules, rate-limit submissions, and provide moderation. |
| Peak traffic | Dining decisions happen around concentrated meal periods. | Cache aggregates and optimize indexed queries. |
| Notification reliability | External notification delivery can fail. | Record notification status and retry appropriate failures. |
| Verified visits | Actual meal-swipe verification may require an unavailable external system. | Treat transaction-linked verified reviews as a future enhancement unless an approved integration is available. |

**Future Enhancements Include**:
*   Verified-visit reviews tied to an approved meal-plan or meal-swipe transaction
*   Personalized recommendations based on a student's past ratings and dietary preferences
*   Automated trend detection for sudden week-over-week station or item rating changes
*   Push notifications in addition to email/browser notifications
*   More advanced anti-spam and fraud detection
*   Additional GSU dining locations if the project scope expands
